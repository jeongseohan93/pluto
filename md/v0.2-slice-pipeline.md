# aidev — Slice Pipeline Requirements v0.2

## 0. 문서 목적

Telemetry Runner(v0.1) 위에 운영 계층을 얹는 첫 slice다.

목적은 완전한 오케스트레이션이 아니다.

> 요구사항.md 하나를 주면 plan → 승인 → implement → test를 사람 없이 진행하고,
> 정해진 지점에서만 승인을 기다린다.

존재 이유는 조커 완수다. 조커의 실제 slice 하나가 무인 완주되는 순간 v0.2는 완료다.

**로드맵 변경 (README 갱신 포함):**

```text
v0.1  Telemetry Runner            ← 완료
v0.2  Slice Pipeline              ← 이번 (구 v0.3 + v0.4 일부를 앞당김)
v0.3  Workspace 격리               (worktree / 브랜치 / 단계별 커밋)
v0.4  Epic → Slice Planner        (구 v0.2, 뒤로 이동)
v0.5  Codebase Memory
v0.6  Pluto IDE 바인딩 (state.json / live.json → window.aidev)
```

순서 변경 근거: Planner(에픽→slice 자동 분해)는 현재 사람이 직접 하고 있어
없어도 조커가 진행되지만, Pipeline(무인 실행 루프)은 없으면 사람이 자리를
비우는 순간 모든 작업이 멈춘다. 병목부터 푼다.

구 로드맵의 "HTML Dashboard"는 제거한다. desktop(Pluto IDE) 합류 이전의
항목으로, 같은 화면을 두 번 만들 이유가 없다. 팀 공유용 리포트가 실제로
필요해지면 그때 별도 항목으로 되살린다.

## 1. 최우선 규칙

```text
1. 기존 코어 6파일(runner/events/telemetry/storage/reporter/cli)의 로직을 수정하지 않는다.
   cli.py는 pipeline 서브커맨드 추가만 허용한다.
2. 파이프라인 로직과 상태 판정은 전부 Python Core에 둔다.
   v0.2에서는 Pluto IDE를 연동하지 않는다.
   향후 Pluto IDE가 실행/승인 명령을 보내더라도,
   pipeline 상태를 직접 계산하거나 소유하지 않는다.
   (Pluto → 명령 → Python Core → 판단/실행 → state.json → Pluto 표시)
3. 파일 규약은 live.json의 검증된 규칙을 상속한다:
   단일 writer / .tmp → os.replace atomic 쓰기 / reader는 깨짐 관용.
4. 세션 정책(기존 결정 준수): 같은 단계의 실패 복구 = 기존 session resume,
   다음 단계 = 새 session.
5. Windows에서 동작해야 한다. (개발 환경이 Windows다)
```

────────

## 2. 명령

```text
aidev pipeline --repo <경로> --requirement <요구사항.md>
aidev pipeline --resume-slice <slice-id>     # 중단된 slice 이어가기
aidev pipeline --list                        # slice 목록 / 상태
```

주의: `--resume`은 run 단위 세션 재개 옵션으로 이미 존재한다.
slice 재개는 이름 충돌을 피해 `--resume-slice`를 쓴다.

## 3. 단계 루프

```text
Requirement
   ↓
[plan]       runner.execute(phase="plan", safety_profile="readonly")
   ↓          → 산출물을 plan.md로 저장
승인 대기     approvals/plan.md 파일 polling
   ↓
[implement]  runner.execute(phase="implement", permission_mode="acceptEdits")
   ↓          프롬프트 = requirement + 승인 시점의 plan.md
[test]       runner.execute(phase="test") — 테스트 실행 지시, 결과 기록
   ↓
완료 보고     단계별 토큰 / 비용 / 변경 요약 (기존 reporter 재사용)
```

- 각 단계 = 기존 `execute()` 1회 호출. phase 라벨은 기존 PHASES 그대로 사용한다.
- plan 단계는 `safety_profile="readonly"`를 강제한다 (계획 중 파일 변경 금지).
- 사람은 승인 전에 plan.md를 직접 수정해도 된다.
  implement는 승인 시점의 plan.md 내용을 읽는다.

────────

## 4. 승인 규약 — stage-independent gate 모델

승인은 특정 단계에 종속된 기능이 아니다.

> **모든 단계 사이에는 게이트가 존재할 수 있다.**
> front matter의 approval은 어느 게이트를 켤지 선택하는 것뿐이다.

구현은 "plan 뒤 승인" 같은 단계별 분기가 아니라,
매 단계 종료 후 "이 단계의 게이트가 켜져 있는가"를 확인하는 단일 루프여야 한다.
(v0.3의 merge 승인, 이후 browser 검증 승인도 게이트 하나를 켜는 일이 된다)

기본으로 켜지는 게이트: **plan 뒤 1곳.**

요구사항.md의 front matter로 조정할 수 있다:

```markdown
---
approval: plan, implement    # 게이트 추가 지정
# approval: none             # 완전 무인
---
# 밤 페이즈 의사 보호 로직
...
```

- 미지정 → `plan`만.

승인 동작:

```text
승인 대기 진입 → state.json = "waiting_approval:<stage>"
             → .aidev/slices/<id>/approvals/<stage>.md 파일 polling

파일 내용이 "approved"           → 다음 단계 진행
파일 내용이 "rejected: <사유>"    → slice 중단, 사유 기록
```

## 5. 실패 / 쿼터 처리

```text
단계 실패
 ├─ 쿼터류 실패 (사용량 한도)  → state = "quota_wait"
 │                            → 대기 후 같은 session으로 --resume 재시도
 └─ 일반 실패                 → state = "failed", slice 중단
                               (자동 repair 루프는 이후 버전)
```

- **쿼터 감지 방식은 이번 slice에서 확정하지 않는다.**
  실제 한도 도달 시 events.jsonl / stderr.log에 오는 내용을 실측한 뒤
  감지 조건을 갱신한다. 스펙상 요구는
  "쿼터류 실패를 일반 실패와 구분하여 재시도한다"까지다.
- 재시도 대기 시간은 2순위 체계다:
  1순위 — 에러/이벤트에서 quota reset 시각을 파싱할 수 있으면 그때까지 대기.
  2순위(fallback) — reset 시각을 알 수 없을 때만 고정 간격(기본 15분) 재시도.
  재시도 상한이 있어야 한다 (기본 20회).
- session_id는 telemetry가 이미 수집한다. state.json에 단계별로 기록한다.

## 6. 파일 규약

저장은 이원화한다:

```text
[도구의 data/ — 기존 그대로]   run 상세 (events.jsonl, telemetry.json, live.json)
[대상 repo의 .aidev/ — 신규]   프로젝트를 따라다녀야 하는 slice 상태
```

```text
<대상repo>/.aidev/slices/<slice-id>/     # slice-id: 20260815-doctor 형식
 ├─ requirement.md        원본 요구사항 사본
 ├─ plan.md               plan 단계 산출물
 ├─ state.json            진행 상태의 유일한 원천 (단일 writer = pipeline 프로세스)
 ├─ approvals/
 │   └─ <stage>.md        사람이 쓰는 승인 파일 (게이트가 켜진 stage마다 하나.
 │                          예: plan.md, approval에 implement 지정 시 implement.md)
 └─ runs.json             단계 → run_id 매핑 (상세는 data/runs/로 연결)
```

state.json:

```json
{
  "slice_id": "20260815-doctor",
  "status": "waiting_approval:plan",
  "stages": {
    "plan":      {"status": "done",    "run_id": "...", "session_id": "..."},
    "implement": {"status": "pending"},
    "test":      {"status": "pending"}
  },
  "quota": {"waiting": false, "resume_at": null, "retries": 0},
  "updated_at": "2026-08-15T21:04:00+09:00"
}
```

- 용어 구분: 이 문서에서 **slice status**는 최상위 `status` 필드를,
  **stage status**는 `stages` 내부의 `status`를 가리킨다. 혼용하지 않는다.
- slice status 값: `running:<단계>` / `waiting_approval:<단계>` / `quota_wait`
  / `done` / `rejected` / `failed`
- stage status 값: `pending` / `running` / `done` / `failed`
- **stages의 키 집합은 고정이 아니다.** 이후 버전에서 단계가 추가될 수 있다
  (예: browser, review). reader(IDE/watch)는 모르는 stage 키를 만나도
  죽지 않고 그대로 표시해야 한다. 존재하지 않는 단계를 미리 넣지는 않는다.
- 쓰기는 기존 `write_json_atomic` 재사용, 읽기는 기존 `read_json_tolerant` 재사용.
- **state.json은 pipeline 진행 상태의 authoritative source다.**
  Pipeline의 현재 단계, 승인 대기, 실패, quota 대기, 완료 여부는
  다른 소스에서 추측하지 않고 state.json을 기준으로 한다.
- Pluto IDE가 pipeline 진행 상태를 표시할 때는 state.json과 live.json을 읽는다.
  현재 mock인 `window.aidev`의 Run/Telemetry 관련 API는 우선 이 파일들과 연결한다.
- Code Graph, Project Tree, Diff, History 등 pipeline 상태와 무관한 IDE 데이터는
  이후 각 기능의 별도 authoritative source를 사용한다.
  (예: 코드/Diff/History의 원천은 git, 그래프는 commit 기준 재계산 index —
  상세는 각 기능의 문서에서 정의한다)

## 7. 안전핀

- 시작 시 대상 repo의 git 상태가 dirty(uncommitted 변경 존재)면
  실행을 거부하고 사유를 출력한다.
  **이 거부는 v0.3 전까지의 임시 제한(temporary restriction)이다.**
  v0.3의 worktree 격리가 이 제한을 대체하며, 격리 공간 안에서는
  이 검사를 유지하지 않는다.
- plan 단계 종료 후 `git status`를 검증한다 —
  readonly인데 변경이 있으면 slice를 즉시 실패 처리한다. (기존 사후검증 정신)
- 단계별 max_turns 상한을 유지한다 (기본 80).

## 9. Done Criteria

```text
☐ aidev pipeline 한 명령으로 조커의 실제 요구사항 하나가
  plan → 승인 → implement → test를 완주한다.
☐ 승인 대기 중 프로세스를 종료해도 --resume-slice로 이어간다.
☐ rejected: 사유 기록 시 slice가 중단되고 사유가 남는다.
☐ 쿼터류 실패가 일반 실패와 구분되어 같은 session으로 재시도된다.
  (감지 상세는 실측 후 이 문서를 갱신한다)
☐ 기존 pytest가 전부 통과한다 (코어 무변경 증명).
☐ fake_claude 기반 pipeline 테스트가 존재한다
  (승인 대기 / 거부 / 재개 시나리오 포함).
☐ state.json이 6조 규약과 일치한다.
☐ Windows에서 완주를 확인한다.
☐ README의 로드맵과 사용법이 갱신된다.
```
